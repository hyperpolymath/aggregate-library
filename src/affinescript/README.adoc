= AffineScript conformer

`ALib.affine` is the AffineScript reference shape for every aLib overlap
operation, mirroring `specs/<category>/<op>.adoc` one-for-one (the same role
`src/ALib.mres` plays for AffineScript and `lib/` for Elixir).

It is also the *extension-layer* conformer: AffineScript is one cube presented
through six faces (RattleScript, JaffaScript, PseudoScript, LucidScript,
CafeScripto, canonical). The faces are pure surface sugar that lower to these
exact definitions, so conforming once here conforms for all six faces at the
library level. See `docs/EXTENSION-LAYER.adoc` for the full argument and the
faces gallery.

== Affine angle

The collection operations (`map`, `filter`, `fold`, `contains`, `length`,
`empty`) carry affine/borrow annotations that make AffineScript a *stronger*
conformer than a GC'd reference — "consumed exactly once" and "no iterator
invalidation" become type-level guarantees rather than runtime conventions.
The arithmetic, comparison, logical, conditional, and string operations are
total pure functions and conform directly.

== Reconciliation with `affinescript/stdlib/alib.affine`

affinescript already ships a *runnable* aLib conformer in its standard library
at `stdlib/alib.affine` — it compiles and is exercised by the affinescript test
suite (verified green, 457 tests). It currently implements **22** of the
overlap operations.

The two are complementary, not duplicate: `stdlib/alib.affine` is the
authoritative *runnable* impl, while this file is the **spec-complete
extension-layer reference** (all 29 operations in `specs/`), mapping each spec
to its AffineScript shape and to the six faces.

The stdlib impl is missing 7 spec operations: `absolute`, `negate`, `max`,
`min` (arithmetic), `reverse` (string), and the collection `length` / `empty`
(its `length` is string-only). Adding those to `stdlib/alib.affine` would make
the runnable stdlib fully aLib-spec-conformant; until then this reference
covers the gap.

=== Known upstream gap: `substring` argument 3

`substring` takes `(s, start, end)`: zero-based indices in Unicode scalar
values, `start` inclusive, `end` exclusive (see `specs/string/substring.adoc`).
`ALib.affine` here passes `end` straight to affinescript's
`String.substring(s, start, end)`, which (per affinescript's
`stdlib/string.affine` at `9167b04`) takes an end index, so this reference
shape needs no `end - start` conversion. Whether affinescript's
`String.length` / `String.substring` count Unicode scalar values (the unit
`specs/string/length.adoc` now fixes) is not verified from this repository.

The runnable `stdlib/alib.affine` in affinescript does *not* conform. At
affinescript `9167b04` it documents aLib's `substring` as
`(s, start, length)` and passes the third argument to `string_sub` as a
length. Because `string_sub` clamps, that reading passes most vectors but
fails `["hello", 1, 4]` (expected `"ell"`, gives `"ello"`) and
`["hello", 2, 2]` (expected `""`, gives `"ll"`). The fix (convert the end index
to the length `end - start` before calling `string_sub`, and run the aLib
vectors against it) belongs in `hyperpolymath/affinescript` and is an open
cross-repo follow-up; this repository does not edit affinescript. Until it
lands, do not cite `stdlib/alib.affine` as conforming for `substring`.

== Caveat

These are spec-level reference shapes. They are written to canonical
AffineScript idiom and the aLib signatures; running them against
`vectors/<category>.json` waits on an AffineScript conformance runner, which
does not exist yet (`scripts/run-conformance-tests.affine` is an unported
source, not a runnable runner). Per aLib's methodology, implementations
borrow the *method*, not the code.
